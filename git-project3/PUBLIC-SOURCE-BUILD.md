# DS-TH09-AI 3.7.0-test

## 3.7 保命 C2 与设置兼容

本版在视野和注意力限制内提前准备保命 C2。普通放 C 仍追求连爆收益；当可见威胁持续挤满注意力、补充额度不足，或已识别威胁下可走的安全方向很少时，可以在实际储量至少 200 的前提下，为生存启动 C2，允许这次没有理想的连爆收益。

救场复用原有蓄力、释放和恢复流程，记录独立原因并锁定一次准备，避免压力短暂变化导致反复取消。充能完成不等于已经无敌：仍遵守动作门、C1 动作、实际蓄力重置和原生释放确认；未确认会超时退出，释放后有冷却。没有能量、已来不及蓄力或通道封死时仍可能中弹。

判断不读取圈外目标，也不用未纳入注意力对象的精确碰撞时间。避弹路线、毒雾减速、激光几何和四项玩家能力参数保持原规则；救场会改变部分场景的放 C 时机，包括对毒场景，不承诺逐帧动作与旧版完全相同。所有角色共用策略，没有对文特判。

### 原设置菜单继续使用

双击 `set-difficulty.cmd` 的操作、菜单项目、命令行参数和保存方式均保持。仍可设置难度、每秒变向、视野半径及注意力容量/恢复。新包默认 human200、AI=2P、debug_log=false，合法 1P key 与 3.6.1 相同，公开配置中的 key 为空。原生授权模块及输入映射没有更改。

根据人工对照测试，本版将 **unlimited（包括 infinite 别名）默认 plan_interval 设为 1**；其他档位、custom、未知档位回退及无运行配置的 Lua 默认使用 6。新默认 JSON 不再写全局 plan_interval，因此菜单切档会自然选中对应默认值。移动、视野、注意力容量/恢复数值没有提高。

已有 JSON 如果明确写着 `"plan_interval": 6` 或其他有效值，仍优先使用该值，菜单不会删除或改写。希望采用新版档位默认值时，只删除 ai 对象内的 plan_interval 一项，注意相邻逗号；也可以在 unlimited 配置中明确写 1。人工测试未发现可感知的水平变化，不代表所有弹幕下 1 与 6 等效。后续比较请使用同一配置。

### 日志与验证范围

CSV 保留原 182 列的名称和位置，在末尾增加 15 列，共 197 列：救场状态、原因、压力持续量、年龄、C2 准备更新数、已知 TTC、是否已迟、冷却、确认、尝试/释放次数及当前路线证据。`rescue_known_ttc` 是策略使用的上一回调证据，扣除一次更新后按当前 timeScale 换算为预计更新次数；`rescue_route_ttc` 是本回调最终路线的证据，仍为游戏计时单位。-1 表示未知。准备值同样使用 AI 更新次数，充满不代表保护已生效。TTC 都是短时预测估计，不是实际命中倒计时；原有动态激光估速和慢速时钟近似仍保留。日志不会反过来驱动决策，也不是完整逐帧回放。

测试包括低压不浪费能量、压力进入/滞回、真实能量和动作门、C1 转入 C2、释放确认/超时/恢复、暂停/受击/新轮清理，以及圈外和未跟踪对象不能泄漏精确 TTC。毒和激光回归、设置菜单、JSON 到运行 Lua、公开包及独立源码重建分别验证。具体通过计数以本次交付报告为准。

离线测试不代表已经解决所有对文早死场景，也没有重新标定各难度存活秒数。请完整解压新包实战复测，保留日志观察是否减少“有能量但 C2 准备太晚”的受击，以及是否因救场过多提前耗尽能量。

# DS-TH09-AI 3.6.1-test

## 3.6.1修正的是脚本绕过

3.6的慢哈希提高了猜key成本，但授权决定仍在可编辑的PowerShell中。本版保留3.6指定的新key和PBKDF2参数，并把检查放入原生启动器、支持模块和最终1P写键入口。

- 正常启动时，脚本仍先检查key；缺失/错误则按原规则配置实际2P。
- 原生启动器在创建游戏进程前独立验证key。删除脚本检查、伪造1P INI或直接运行启动器，不能跳过此验证；这种被篡改的启动请求会拒绝启动，不悄悄执行1P。
- 游戏内的原生支持模块再次独立验证。只有实际1P、key正确且输入/传感器/保护初始化全部成功，才发布本进程的只读授权结果。
- 发行 `inject.dll` 的1P写键入口会检查该结果。缺少支持模块/导出、授权失败或只启用2P时，都不执行1P写键。因此改INI、换上游启动器或单独加载本版注入DLL，也不会直接获得1P控制。已有2P写键与键位逻辑保留。

新增入口检查由公开的构建工具根据已验证的原版DLL确定性生成，保留原有函数RVA；随包源码能独立重建并校验它。不要混用旧inject.dll或window_support.dll，整包解压使用。

key只经短暂的进程环境传给原生模块，不写入命令行、INI、Lua、日志或额外授权文件。原生模块自行计算PBKDF2，不信任脚本传来的布尔值或公开摘要。父进程创建子进程后清除传递变量，支持模块验证后清除其副本；不声称能防同权限进程读取内存。

合法key无需更换。公开默认仍为 `ai.side=2, ai.side_key=""`；启用1P时在已有JSON的ai对象中填 `side=1` 和3.6指定的新key。key精确匹配，新增拒绝NUL字符，避免环境传递截断和HMAC尾部零字节等价。校验仅在启动阶段执行，战斗中只是轻量授权状态检查。Windows PowerShell5.1/.NET Framework4.7.2+要求保留，原生使用Windows CNG。

这版覆盖修改脚本/INI、换入口时对本版原生模块的绕过。重编译源码、替换/修改DLL、直接改进程内存、使用旧包或另写AI仍可另行绕过，本地公开源码程序不能对此提供不可撤销授权保证。

## 难度基线保持不变

没有修改plan_interval，没有按对手角色切换参数。发行配置仍为6；移动预算、圆形视野、注意力容量/恢复以及避弹、对毒、放C逻辑均保持3.6。日志版本号更新为3.6.1，列数仍182。

把plan_interval从6改为1会缩短新目标进入避弹判断的等待，属于能力设定变化。即使另外四项参数不变，也应视为不同的参数基线；只对文改变它，不能拿来宣称原档位的统一基线没变。此前报告仅提出对照实验，本版没有替你执行这项调整。

## 构建和验证范围

目标包 `DS-TH09-AI-v3.6.1-test.zip`。开发目录运行build-native.ps1，再运行build-public-package.ps1（Version为3.6.1-test）；完整解压包可在source目录运行rebuild-from-package.ps1并提供完整TinyCC0.9.27 win32的CompilerPath。构建无须有效key。

验证包含篡改脚本/INI、父启动器检查被跳过时的支持模块拒绝、真实x86写键入口拒绝/授权路径、原参数与输入回归、独立源码重建。本轮不运行游戏主线程，实际计数见交付验证说明；不以离线测试代替实战验收。

# DS-TH09-AI 3.6.0-test

## 本版变化

基于3.5，轮换1P配置key并加强启动校验，同时补充对文等高速压力场景的诊断。灵梦C1修复保留；本版没有调整避弹、放C、毒处理或四项能力参数，不代表已经修好对文的生存表现。

### 1P配置key

请求 `ai.side=1` 时使用本次重新指定的key，旧key在3.6中不再有效。源码只保存随机盐及 PBKDF2-HMAC-SHA256 校验结果，迭代600000次；不保存key明文，也不回退到旧的快速SHA256校验。旧包保持原样，不会因本版发布自动撤销其中的旧key。

公开默认仍为 `ai.side=2, ai.side_key=""`。需要1P时，关闭游戏，在已有 `launcher-settings.json` 的 `ai` 对象内填写 `side=1` 及新的 `side_key`；区分大小写，空格也参与校验。不要分享已填私人key的配置。启动时显示的实际接管侧为准。

缺失、错误、非字符串或超长key回退实际2P，不改保存的JSON；side本身仍必须是整数1或2。实际侧继续决定唯一AI输入、真人侧、Charge Type=Slow要求和1P练习保护：实际AI为1P时不为AI开启练习保护，回退2P时按原设置保护真人1P。

1P校验需要 Windows PowerShell 5.1 及 .NET Framework 4.7.2或更新版本；缺少所需加密API或加密失败时回退2P，不降级为弱校验。600000次计算只在请求1P的启动阶段执行，本机测得约1.4～1.7秒；2P跳过，战斗期间不计算。逐字节比较没有提前退出，但不宣称PowerShell执行具有严格恒定时间。

这是提高离线猜测成本的本地门槛。持有源码者仍能改掉检查，它不提供在线授权或防篡改保护。

### 日志增强

开启 `ai.debug_log=true` 后，CSV共182列，3.5的前169列名称和顺序不变。尾部追加版本、实际AI侧、双方角色编号、实际扫描间隔、是否扫描、未跟踪目标计数、信用/容量拒绝计数、恐慌状态，以及蓄力速度、预热更新数和时间比例。角色未知记为-1；缺失的时间信息留空。

出现/消失紧急盲弹、过载状态变化、移动风险变化时增加记录，仍保留原来的周期和动作/受击记录。它不是逐帧录像，也没有记录致命子弹ID或完整命中前缓存。`attention_waiting_scan_count` 是未扫描回调中当前相关但未跟踪的目标数，不表示扫描间隔是唯一原因；信用与容量拒绝按实际扫描时的纳入结果计数，两者可以重叠。

### 对文的对照测试

已有日志确认两轮对文首次受击约113、120秒，一轮对毒约167秒；文的6次受击中5次记录到紧急盲弹，也有储量足够但C2尚未蓄好的窗口。日志无法确定每次具体致命对象，不能据此把所有死亡归因于注意力。

默认 `plan_interval=6` 保留。建议另存一份对文测试配置，仅把已有 `ai.plan_interval` 改为1，保持 unlimited、移动预算6、圆形视野149.3333、注意力容量120/恢复90不变，并使用相同双方角色作多轮对照。它缩短新目标纳入的等待，不增加注意力额度，不保证解决信用耗尽或C2准备过晚。对毒继续使用原配置。

## 本版变化

3.5 基于已验收的 3.4 继续开发，处理灵梦 C1 相关问题，并给 1P AI 接管增加本地配置 key 门槛。原有两侧键位、四项能力参数和默认 2P 接管方式保留。

灵梦 C1 现在区分“预测碰到”与“预计足以起爆”：读取同一个目标的实际血量、受伤状态及固灵状态，结合符札伤害、追踪路径和首次碰撞判断。单张伤害不足不会凭空计整条连爆；前方目标消耗的非贯穿符札不能再次给后方目标计算伤害。未固灵不能直接作为 C1 起爆种子，固灵准备仍须观察到同一目标实际激活，不能只因请求过 Shift 就视为成功。

预测计入剩余充能时间以及符札先展开、后追踪的过程；蓄力后持续复核原来的直接起爆目标。未满 C1 时目标失效可取消，蓄满后只作有界等待，并防止误升 C2。原有期限型 C1 和 C2 的独立规则保留，不把有意的期限释放误报为可靠连爆收益。

新增读取和估计不会改写游戏血量、判定或子弹。避弹与 C 目标继续受同一圆形视野限制，Shift 仍服从实际避弹输出和原来的时间预算。预测只使用当前可见目标及有限时间窗口；目标以后转向、消失、入场或特殊受伤状态仍可能令实际结果不同，本版不承诺每次 C1 必然打爆目标。

## 选择 AI 接管侧

关闭游戏，用记事本编辑 `launcher-settings.json` 中已经存在的 `ai` 对象，保留其他参数。默认字段为：

```json
"side": 2,
"side_key": ""
```

以上是对象内的字段片段，不是完整 JSON 文件；不要新建第二个 `ai` 对象或用片段覆盖整个设置文件。

- AI 在右侧 2P：保留 `"side": 2`，不需要 key。
- 请求 AI 在左侧 1P：设为 `"side": 1`，并把获得的 key 填入同一对象的 `side_key` 字符串。key 区分大小写，不自动去掉首尾空白。
- 请求 1P 时，key 缺失、错误或不是字符串，启动器会提示本次改用 2P AI。原文件中的 `side`、`side_key` 和练习设置保持不变。
- `side` 缺失时按 2P 处理。`side` 本身仍只允许数字 `1` 或 `2`；其他值或字符串 `"1"`／`"2"` 会报错停止启动，不会按 key 回退规则放行。

更改后重新运行启动脚本。以启动控制台显示的**实际接管侧**为准：

| 保存的请求 | key 状态 | 实际 AI 侧 | 玩家侧 | 必须使用 `Charge Type = Slow` 的一侧 |
| --- | --- | --- | --- | --- |
| `side=2` 或未设置 | 不要求 | 2P | 1P | 2P |
| `side=1` | 正确 | 1P | 2P | 1P |
| `side=1` | 缺失／错误／类型不符 | 2P | 1P | 2P |

玩家侧可保留自己的 Charge Type。它与 Key Config 的键盘 Type 是不同设置。

`side_key` 只参与启动器的本地判断，不传入生成的 INI 或 Lua 设置，也不在启动提示和日志中显示。公开默认值为空，代码保存校验摘要。这是**本地配置门槛，不是在线账号授权**；能修改源码的人可以修改或绕过该判断，因此不把它当作远程权限或防篡改机制。

`ai.enabled` 仍然是注意力限制的开关，不表示启用或停用机器人接管。

## 练习保护跟随实际接管结果

旧字段 `practice.player1_no_damage` 和 `practice.player1_invincible` 始终只表示左侧 1P，没有新增 2P 练习保护。

- 实际 AI 为 2P：1P 是玩家，按保存的配置应用 1P 练习保护，包括请求 1P 但 key 未通过的回退情况。
- 实际 AI 为 1P：自动抑制两个 1P 练习开关的生效，防止保护机器人。原 JSON 值保留，也不会转移为保护右侧玩家。

2.0.5继续优化全角色开花：分别比较普通起爆目标和固灵收益，灵群在侧面时先尝试高速预靠近，再短暂低速固灵，保留原链并避免同时过早点火。固灵价值包含周围妖精／灵和白弹资源；已有200能量但C2收益不足，不再无条件覆盖固灵靠近意图。预靠近默认最多60次更新，受阻后退出并保留重试间隔；整个准备／等形状仍有90次更新上限。

C1开始使用只读的角色发射模板和本方已生成C1攻击的当前矩形判定，估计能起爆哪些链，以及是否比提前C2保留更多白弹。支持范围取决于该角色模板和回调：无法核实的自定义生成、运动或命中行为采用有限模型／既有回退，不能声称所有角色C1都已精确模拟。正在执行的C1剩余作用与下一次新蓄力C1的收益分开，不重复预算。

C2松Z以后，只有观察到蓄力重置及关联的新保护／共同波，才进入后续窗口。输入门允许且当前链有用时可再按Z，经营角色攻击或预持下一次蓄力；这个Z请求单独计数，不冒充又成功释放了一次C1，也不绕过蓄力动作门。

默认高速间隔仍为72次更新。仅在已确认C2后且真实剩余保护足够时，短固灵可在高速24次更新后开始；实际Shift预算仍为每180更新最多40次，单段最多32次，资源、对齐和动作条件仍须满足。这是保护窗内的有限例外，不持续按住Shift，也不降低原避弹强度。

实际共同消弹圈按固定中心、半径、延迟和剩余寿命读取，可能被圈直接吞掉的白弹不计回能或返弹。共同圈不是C2专属标记；C2直接起爆妖精／未固灵与普通枪起爆条件仍分开。圈与爆风的竞速仍是估计，不能把预计清除区域当作已无弹的安全区。

后续走位使用真实state3剩余保护，并额外检查短程落点在保护结束后是否仍可停留。原12更新运动轨迹、毒减速、激光／EX几何和Y≥150限制保留；扩展只在正常时间尺度的已确认窗口启用，检查至保守到期后4更新、总域最多60，不把持续朝一个方向跑到远处当作必经路线。无可靠落点时保留即时避弹，不能保证长期围堵中的生存。

独立8秒C2节奏、C1不重置C2计时、只主动C1/C2、无X、50万不停枪和非随机C继续保留。C2可在200～299、C1在100～199有界等形状（最多24更新）；白弹将漏过、准备到限、期限或下一更新将跨等级时结束等待。8秒是480游戏Timer目标，缺能／动作门／受击仍可能延期；切入与时停冻结节奏。3.0避弹降级及压力C3/C4仍未实施。

## 从下载包重新编译

需要 Windows、Windows PowerShell 5.1 或更新版，以及完整的 **TinyCC 0.9.27 win32/i386** 便携工具目录。不要只复制 `tcc.exe`，它还需要相邻的 `include`、`lib` 和运行库文件。官方工具下载：

[tcc-0.9.27-win32-bin.zip](https://download.savannah.gnu.org/releases/tinycc/tcc-0.9.27-win32-bin.zip)

该官方 ZIP 的 SHA-256：

```text
02E2BFE8C272A549B15E4BFA4507BD7E05304692AF1761DB6C1E8E88AF675651
```

完整解压 TH09-AI，保留其 `source`、`runtime`、`licenses` 和玩家文档的相对位置。在 `TH09-AI/source` 打开 PowerShell，例如工具解压到 `C:\tools\tcc` 后运行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\rebuild-from-package.ps1 -CompilerPath 'C:\tools\tcc\tcc.exe'
```

脚本首先检查输入，然后只向当前 `source/dist` 和 `source/work` 写入。它从上一级发行目录复制未修改的 `runtime/ka_ai_duka.exe` 与 `runtime/inject.dll`、第三方许可/源码包、玩家文档、版本、配置和发布说明作为构建基线；不会递归复制上一级 `source`，也不会复制游戏或运行生成的 INI、日志。之后从本包 C 源码重新生成 `th09ai-launcher.exe` 与 `window_support.dll`，运行自建隐藏窗口测试、隔离的激光感知自测，以及自机／毒云状态与x86桥接自测，再复制 Lua/启动脚本并打包。

`laser_sensor_selftest.c` 故意不加载上游 DLL 来验证安全拒绝路径，因此会先输出 `laser_sensor: install=FAILED reason=verified upstream inject.dll is not loaded`，随后输出 PASS。这是隔离测试的预期输出，不等于真实游戏启动失败；若实际启动的 `runtime/native-window.log` 出现感知安装失败，仍应停止并排查，不能忽略。

输出是：

```text
source/dist/TH09-AI/                    重建的可运行包
source/dist/TH09-AI-v2.0.5.zip           含源码的新压缩包
source/work/native-tests/              本机构建测试文件
```

默认版本是 `2.0.5`。已有同名 ZIP 时默认拒绝覆盖；可用 `-Version 2.0.5-local` 指定另一个名字，或明确添加 `-Overwrite`。自定义版本仅标识本地构建，不表示原发行者审核了修改。再次生成源码快照时，旧的生成目录会移到 `source/work/public-source-backups`，不会悄悄删除。旧 `2.0.4`、`2.0.3`、`2.0.2`、`2.0.1`、`2.0.0` 和 `0.1.9` ZIP 请保留为独立回退副本。

改动 `source/src` 后重新运行上面的命令即可重新编译和链接；源文件可审阅、修改、供个人使用。重建不需要游戏本体，也不会修改上一级原发行目录或任何游戏配置。若要试玩，请把**新生成的** `source/dist/TH09-AI` 另行放到你的 TH09 游戏附近；重建脚本本身不启动游戏。

维护者在完整工程中使用 `build-native.ps1 -CompilerPath ...` 编译，然后用 `build-public-package.ps1 -Version 2.0.5` 生成带源码的发行包。后者严格选择所需源文件，不复制项目根目录中的其他资料。缺少许可、源码或上级发行必需文件时，脚本会明确失败；不要用空文件绕过检查。

## 修改 TinyCC 启动库并重新链接

本包原生模块静态链接了 TinyCC 0.9.27 的启动/辅助代码，包括 `win32/lib/crt1.c`、`win32/lib/dllcrt1.c` 和 `win32/lib/chkstk.S`。这部分适用其独立的 LGPL 2.1 许可；许可正文和说明位于上一级 `licenses/tinycc`。完整对应源码在：

```text
../licenses/tinycc/tcc-0.9.27.tar.bz2
SHA-256 DE23AF78FCA90CE32DFF2DD45B3432B2334740BB9BB7B05BF60FDBFC396CEB9C
```

源码归档中个别文件具有自己的许可声明，例如 `lib/libtcc1.c` 的 GPL 2 或更新版本及其编译后链接例外；应保留并遵守这些声明。同目录还提供 `GPL-2.0.txt`，不能把链接例外理解成源码再分发也不受其许可约束。

你可以修改这些库并重新链接我们的模块，也可以为个人使用、调试该修改或排查兼容性问题进行必要的分析和逆向工程；本项目不会用额外限制阻碍第三方许可授予的这些权利。第三方组件继续各自遵守其许可，项目主许可不会取代它们。本包提供构建我们的两个原生模块所需的完整源文件和脚本，因此重新链接修改后的库无需向我们索要专用 `.obj` 文件。

下面的参数依据随包源码中的 `win32/build-tcc.bat` 和 `win32/tcc-win32.txt`。请在单独的开发目录解压源码，修改目标库文件，然后从解压后的 `win32` 目录构建。示例中路径刻意不带空格，以兼容上游批处理的参数处理：

```powershell
# 把源码归档解压到一个新建的独立开发目录（路径可自行调整）。
New-Item -ItemType Directory -Path C:\tcc-src-0.9.27
tar -xjf ..\licenses\tinycc\tcc-0.9.27.tar.bz2 -C C:\tcc-src-0.9.27
Set-Location C:\tcc-src-0.9.27\tcc-0.9.27\win32

# 先编辑 lib\crt1.c、lib\dllcrt1.c、lib\chkstk.S 等需要修改的源文件。
# 使用位于另一个目录的现成 win32 编译器自举，并输出到新的完整工具目录。
cmd.exe /d /c build-tcc.bat -c C:\tools\tcc\tcc.exe -t 32 -i C:\tools\tcc-modified
```

`-c` 选择现成的构建编译器，`-t 32` 强制默认目标为 i386，`-i` 把产物、头文件和库安装到指定的新目录。**不要加 `-x`**：它只生成编译器可执行文件，会跳过库。上游脚本会用新编译器编译 `crt1.o`、`dllcrt1.o`、`chkstk.o` 等，并用 `-m32 -ar` 生成 `lib/libtcc1-32.a`；它同时还构建 64 位交叉产物，但我们的模块仍使用 i386 编译器。

该上游批处理会清理其源码 `win32` 目录内已有的编译输出，所以应在上面单独解压的开发副本中运行，并把现成编译器放在不同目录。构建成功后检查新目录中的 `tcc.exe`、`lib/libtcc1-32.a` 和 `include` 均已生成。然后回到本包 `TH09-AI/source`，用新的完整编译器目录重建：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\rebuild-from-package.ps1 -CompilerPath 'C:\tools\tcc-modified\tcc.exe' -Version 2.0.5-modified
```

编译器会从自身目录查找刚修改并重建的启动库，两个原生模块会重新链接该库。请保留你的库源码修改和相应许可，在分发修改版本时一并处理适用许可要求。上述操作不需要安装系统级编译环境，也无需提供或打包 TH09 游戏文件。
